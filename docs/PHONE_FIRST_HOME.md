# 전화 중심 메인페이지와 후속 연동

## 제품 방향

`070-5276-7681` 시범 전화 → 실시간 전사 초안 → 사람의 검토 → 초기 대응 분석·확인 카드 → 대응 기록.

전화는 상황 전달의 입구, 지역·소방서 선택은 상황실과 소방대원의 대응 화면 진입으로 함께 강조한다.
화면은 검토·판단 지원, 기록은 인계·재검토를 위한 단계로 구분한다.
이 번호를 공식 119 접수나 자동 출동 서비스로 안내하지 않는다.

## 이번 변경 범위

- `/` 첫 화면에 전화 CTA와 번호 복사를 배치한다. `tel:` 링크는 단말의 전화 앱을 열 뿐, 브라우저 사고와 통화를 연결하지 않는다.
- 사용자 제공 기존 화면을 기준으로 **왼쪽 소개 + 오른쪽 통합 진입 카드**를 유지한다. 긴 가로 섹션으로 나눈 재설계는 채택하지 않는다.
- 전화·번호 복사·시범 안내는 왼쪽 소개 문구 아래에, 지역·소방서 선택→짧은 브리프는 오른쪽 카드에 배치해 높이를 분산한다. 선택 폼은 항상 펼쳐 두고, 왼쪽 대응 화면 버튼은 해당 폼으로 이동한다. 모바일은 소개·전화→지역 선택 카드 순서로 쌓는다.
- 상황실은 신고 내용·전사 검토, 현장 소방대원은 물질 후보·근거·확인 사항을 보는 용도로 설명한다. 별도의 역할 인증이나 화면별 권한을 새로 구현한 것은 아니다.
- 지역·소방서 선택 후 기존 `/main` 경로와 `{ region, station }` 전달을 유지한다. `/onboarding` 경로 자체도 변경하지 않는다.
- 브리프 제목·본문·검토 안내를 세로 블록으로 분리한다. 예시 신고문은 실제 통화/분석 결과가 아닌 모의 문구로 표시한다.
- 전화 전사 연결, 기록 조회를 이미 완성된 운영 기능처럼 표시하지 않는다.
- Backend, 전화 gateway, API 계약, records 구현, 인증, 운영 배포는 수정하지 않는다.

## 다음 개발 순서

1. **통화와 사고 연결:** 서버에서 `callId`·로그인 세션·`incidentId`를 연결하고 접근 권한을 검증한다. 지역 선택만으로 연결됐다고 표시하지 않는다.
2. **전사 수신:** `INTERIM`은 임시 표시, `FINAL`도 검토 대기로 둔다. 끊김·중복 이벤트·다른 사고 이벤트·재접속 처리를 검증한다. 대기/수신 중/종료/검토 대기/오류를 구분한다.
3. **검토 후 분석:** 원문과 사용자의 수정본을 구분하고 검토한 버전만 분석한다. 늦게 도착한 전사나 이전 분석이 최신 상태를 덮어쓰지 않게 한다.
4. **확인·지원 카드:** 미확인 단계는 정보 확인 질문, 확인 후에는 적용 조건과 출처가 있는 참고 카드로 구분한다. 두 CAS 확인은 조합 규칙 실행 조건이지 전술 승인 조건이 아니다.
5. **기록·재검토:** 검토 입력 버전, 확인/취소 이력, 분석 결과 버전과 근거, 사용자 조치를 연결한다. 보관 기간·접근 권한·삭제 정책을 결정하기 전 원문 보존을 확대하지 않는다. 목록·상세는 별도 records 작업과 연계한다.
6. **통합 검증 후 문구 변경:** 개인정보 없는 모의 통화로 전사→검토→분석→기록 조회를 검증하고 장애 시 수동 입력 경로를 확인한다. 성공한 범위만 “연동 검증 중”에서 변경한다.

전화 제공자의 녹음·전사 보관 정책과 동의 절차 확인은 별도 선행 조건이다.
전화 수신 자체를 위해 이번 UI 작업에서 실제 전화를 걸거나 녹음을 수집하지 않는다.

## 검증 방법

```bash
corepack pnpm install --frozen-lockfile
corepack pnpm test src/components/welcome/OpenSection.test.tsx
corepack pnpm check
corepack pnpm dev --host 127.0.0.1 --port 5188 --strictPort
```

브라우저에서 `/`를 열어 다음을 확인한다.

- 320 / 390 / 768 / 1024 / 1440px: 전화번호와 브리프에 가로 잘림이 없고 제목·본문·안내문이 겹치지 않는다.
- 번호 복사 성공·실패 안내, 키보드 포커스, 지역·소방서 선택 영역의 상시 노출과 지역 변경 시 소방서 초기화.
- 전화 버튼은 링크 대상만 확인하고 자동화로 발신하지 않는다.
- 표시 예시를 실제 API 평가나 전화 E2E 검증으로 기록하지 않는다.
